## 2. Source availability for claimed native C++ patches — DECISIVE FINDING

**The public repository does NOT contain Chromium C++ patch sources.**

| `README.md`: claims **"87 source-level C++ patches — canvas, WebGL, audio, fonts, GPU, screen, WebRTC, network timing, automation signals, CDP input behavior"** compiled into the binary                                                                              | README.md, v0.6.3 section + "How It Works"                              |
| `README.md`: "The binary includes 87 source-level patches… compiled into the Chromium binary — not injected via JavaScript, not set via flags" + Ed25519/GPG/Cosign signed downloads                                                                                   | README "How It Works" + "Security"                                      |
| `CHANGELOG.md` (81 KB): tags entries as **`[wrapper]`** vs **`[binary]`** — but `[binary]` entries are _descriptions of behavior shipped in the proprietary binary_, not patch sources                                                                                 | CHANGELOG.md (head scanned, v0.6.3 section in the release commit patch) |

**Conclusion:** the claimed "source-level C++ patches" are **compiled into the proprietary distributed binary (CloakBrowser Pro/Stable)** and are **NOT available as public source code**. The public repository provides only the Playwright/Puppeteer wrapper (Python/JS/.NET), the download+signature-verification logic, the humanize engine, and tools (`cloakserve`/`cloaktest`). Only the v146-era free binary (58 patches, older Chromium 146) remains available via GitHub Releases without a subscription; the v154/current binary requires CloakBrowser Pro (active paid subscription or free GitHub sign-in for 1 concurrent session). No reproducible C++ patch source, no Chromium build scripts, and no engine reproducibility recipe exists in the public repository.

### Root cause assessment for the Novellive case (from tested evidence)

The most probable root cause is **the Electron/Chromium version and TLS/protocol fingerprint gap with current Chrome**. Evidence: (a) fresh temp profiles on both — not cookies/profile state; (b) same network; (c) CF did issue a passive "checking" challenge to both but let Chrome pass in <3 s while never letting Min past it (90 s timeout). This is the well-documented Electron/Chromium-lag issue for Cloudflare's newer detection code.

This root cause would require an **Electron/Chromium upgrade, or an alternate-engine path** — neither is fixable at the application level. Fix is tracked to the Phase C native-engine decision. User-facing workaround: use Chrome for the affected domain, or use a proxy/endpoint to let the challenge clear (outside Min's scope).

### Harness-architecture note (for THIS task's comparison table perspective, M2/M3 ideas from §4)

The Cloudflare challenge is invisible to Min's main-frame browser_eval — **the challenge content lives in an injected iframe/shadow-DOM** and won't appear in a top-level `document.body` search. An architecture telescope that assesses what would happen: this is exactly the "fingerprint and anti-bot evasion" class the Master Scope Register has reserved for Phase C (CloakBrowser's C++ patch set).

## 7. Novellive diagnostic protocol (if reproduction is impossible on a given host)

1. Record the challenge provider and classification (Cloudflare based on `cf-mitigated` header / `cf-ray` / `challenge-platform` body tag; confirm from HTTP response headers, not the page title).
2. Compare Min vs Chrome on the same host, network, and exact URL, using fresh temp profiles (no pre-existing cookies). Record elapsed-to-clear, redirects, and whether the check is ambiguous.
3. In Min, capture sanitized console/network errors. Confirm that `challenges.cloudflare.com` request/response are NOT blocked by the ad-blocker/filtering (if blocked, propose a narrow reversible rule fix, not a global filter disable).
4. Compare Min and Chrome on their Chromium/Electron version, TLS handshake, HTTP/2 header order. Do not assume a single fingerprint field.
5. Add a reproducible cross-browser regression fixture if the root cause is application/configuration level. Do not auto-solve challenges.
6. Do not record challenge tokens, cookies, or auth headers.
